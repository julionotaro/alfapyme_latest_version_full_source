Recomendación de arquitectura mínima sensata 

 

Mover la ingestión crítica a un backend como microservicio (HTTP API) que reciba PDF/imagen y devuelva: texto, bounding boxes, document type, extracted fields, decision. Esto hace la capa testable con scripts Node/CI y permite reutilizarla desde web, email, WhatsApp y backoffice. Razonamiento: los motores modernos como PaddleOCR ofrecen determinismo y mejores resultados que tesseract.js en producción; además, ONNX/PP‑OCR puede correr en Node y ser versionada para reproducibilidad. [^1] 

 

Mantener una versión ligera en frontend para UX (previsualización, redacción local) pero no como fuente de verdad para decisiones finales. El backend es la única fuente de verificación. 

 

Pruebas reproducibles: almacenar fixtures (PDFs, images) + expected outputs (texto, fields, decision). Ejecutar pipeline en CI contra esos fixtures y comparar hashes/text diffs; registrar artefactos (OCR output, images with boxes) para auditoría. 

 

Alternativas a tesseract.js y patrón híbrido 

 

Self‑hosted PaddleOCR via ONNX en Node: mejor estructura/layout handling y determinismo frente a tesseract.js; se puede ejecutar en CPU y es reproducible en contenedores. [^1][^2] 

 

Cloud OCR (Google Vision / AWS Textract / Azure Read) para fases de validación o cuando la precisión supera el coste; útil como fallback o para entrenamiento de reglas de extracción. Precios y capacidades varían por proveedor. [^3] 

 

Camino más corto y serio para cerrar ahora 

 

Keep current frontend code but add a small backend wrapper: a Node service that can run the same OCR (or call tesseract.js/Paddle via ONNX) and expose an API. 

 

Create CI job that runs the frontend ingestion inside a headless browser against stored fixtures (PDFs/images) and also runs the backend OCR on the same fixtures; assert outputs match expected fields and final decision. This gives immediate reproducible evidence without full rewrite. 

 

If time is very short, run backend OCR only on fixtures and produce a signed report (input hash, OCR text, detected type, fields, decision) as verifiable evidence. 

 

Riesgos y notas prácticas 

 

Tesseract.js es gratuito pero menos robusto en layouts y tablas; para producción considere PaddleOCR o cloud APIs según coste/privacidad. [^4][^5] 

 

Determinismo se logra fijando versiones de modelos, contenedores y test fixtures; registre artefactos para auditoría. [^1]

Hablemos de negocios y de arquitectura real. El problema que enfrentan con Alfa-Pyme es un clásico cuello de botella en etapas tempranas de desarrollo: delegar procesamiento pesado a la capa de presentación. 

​Hacer OCR y parseo de PDFs en el navegador es como pedirle al recepcionista de una oficina que no solo reciba los documentos, sino que los traduzca, los analice y tome decisiones legales, todo mientras atiende el teléfono. Eventualmente, el navegador (el recepcionista) colapsa, consume excesiva memoria (especialmente con PDFs escaneados de múltiples páginas típicos en gestorías) y, como ya han notado, vuelve el testing una pesadilla. 

​Aquí tienen mi análisis directo, respondiendo a sus preguntas y proyectando la solución hacia ese futuro omnicanal, asegurando que el piloto con los gestores administrativos fluya sin fricciones técnicas. 

​El camino más corto para cerrar la validación hoy (Sin rehacer todo) 

​Si el mandato de negocio es “validar de forma reproducible ya” sin tocar el código de React, la respuesta no es un script de Node (que no soporta las APIs de Canvas o FileReader de forma nativa sin hacks horribles como jsdom). 

​La solución técnicamente seria es Playwright (o Cypress, pero Playwright es más rápido y robusto para esto). 

​¿Por qué? Playwright levanta una instancia real de Chromium (headless). 

​La ejecución: Escriben un test automatizado que interactúe con su <input type=”file”>, suba el PDF con texto, el PDF escaneado y la imagen. Luego, el test espera a que su frontend termine el procesamiento y captura el estado final (texto extraído, decisión) directamente del DOM o interceptando los logs de consola/estado de React. 

​Resultado: Tienen evidencia fiable, reproducible en cualquier máquina o CI/CD (GitHub Actions), y cero hacks. 

​¿Frontend vs. Backend? (La decisión arquitectónica) 

​A corto plazo (hoy), mantengan la lógica en el frontend y testeen con Playwright para sacar la validación adelante. 

​A medio plazo (la semana que viene), deben mover la ingestión y el OCR al backend. 

Mantener esto en el frontend es un suicidio arquitectónico si el objetivo es habilitar canales como WhatsApp, Email o procesos en lote. Un mensaje de WhatsApp con una foto de un DNI no pasa por un navegador web; necesita un endpoint (webhook) que reciba el archivo y ejecute el mismo pipeline de triaje que la web. 

​La arquitectura multi-canal (El siguiente paso mínimo sensato) 

​Para que Tyrion pueda escalar y recibir documentos desde cualquier frente, necesitan un patrón centralizado y asíncrono. Esta es la arquitectura que evitará que se peguen un tiro en el pie cuando integren el segundo canal: 

​Capa de Recepción (Los “Tentáculos”): La app de React, el webhook de WhatsApp o el parser de correos solo hacen una cosa: recibir el archivo y enviarlo a un Object Storage (como un bucket de S3 o Supabase Storage). 

​Cola de Procesamiento (El “Buffer”): Al subir el archivo, se dispara un evento que entra en una cola de tareas (ej. BullMQ en Node, o un background worker simple). Esto evita que el backend colapse si entran 50 documentos de golpe. 

​Motor de Ingestión y Triaje (El “Cerebro”): El worker del backend descarga el documento, extrae el texto, estructura los campos y toma la decisión. 

​Retorno: El resultado se guarda en base de datos. El frontend (React) simplemente hace polling o recibe un evento por WebSocket indicando “El expediente X ya fue procesado, aquí está el resultado”. 

​La alternativa a tesseract.js (El as bajo la manga) 

​Tesseract.js en el frontend descarga modelos pesados en el cliente, drena la batería en móviles y su precisión con documentos de baja calidad (típicos de oficinas) es mediocre comparado con soluciones modernas. 

​El patrón híbrido más inteligente para ustedes: 

Ya que Tyrion está orquestado con la familia de modelos Gemini 1.5 Flash, tienen la solución en sus manos y no necesitan Tesseract en absoluto. 

​Gemini 1.5 Flash es nativamente multimodal y brutalmente rápido. En lugar de hacer OCR (Tesseract) + Regex o LLM para extraer campos, pueden matar tres pájaros de un tiro enviando el documento (PDF o Imagen) directamente a la API de Gemini desde el backend con un prompt estructurado: 

​“Eres un sistema de triaje. Analiza este documento. Devuelve un JSON estricto con: 1) Tipo documental, 2) Texto íntegro extraído, 3) Campos clave (NIF, importes, fechas), 4) Decisión del expediente.” 

​Ventajas de este enfoque: 

​Coste/Beneficio: Flash es extremadamente económico e infinitamente superior en precisión a Tesseract, especialmente entendiendo la estructura de facturas, contratos y formularios mal escaneados de gestorías. 

​Simplicidad: Reducen un pipeline de 4 pasos (Lector PDF -> OCR -> Extracción -> LLM) a una sola llamada a una API. 

​Robustez: Resuelve el problema de los PDFs con texto embebido, escaneados e imágenes de un solo plumazo.

Mejor estrategia para testear el pipeline actual sin rehacerlo 

 

Respuesta corta: automatización de navegador con Playwright. 

 

Tu pipeline ya depende de pdfjs-dist (que usa canvas, DOM, workers) y tesseract.js (que corre sobre Web Workers y canvas). Intentar ejecutar eso en Node con polyfills (jsdom, node-canvas, etc.) es una trampa: requiere mantener un entorno frágil, desincronizado del real y no garantiza que el comportamiento sea idéntico al del navegador. 

 

La vía más rápida y fiable es usar Playwright (o Puppeteer) para: 

 

1. Levantar el servidor de desarrollo de Vite (o el build). 

2. Navegar a la página de triaje. 

3. Inyectar los ficheros de prueba (los tres casos) mediante page.setInputFiles() sobre el <input type=”file”>. 

4. Disparar la lógica de extracción tal como lo hace el usuario. 

5. Capturar los resultados desde el DOM o, mejor, exponer en window.__result un objeto con: texto extraído, tipo documental, campos y decisión. 

6. Validar con aserciones de Playwright (expect) y generar evidencias (capturas de pantalla, logs, incluso volcar JSON a un fichero). 

 

Esto es reproducible, se puede ejecutar en CI (GitHub Actions, GitLab CI) con navegadores headless, y no toca nada del código de producción salvo la pequeña exposición de resultados en modo desarrollo si quieres simplificar la captura. Además, te da la misma fidelidad que el usuario final. 

 

Ejemplo mínimo de test con Playwright: 

 

```ts 

// test/triaje.spec.ts 

Import { test, expect } from ‘@playwright/test’; 

Import path from ‘path’; 

 

Const casos = [ 

  { nombre: ‘PDF texto embebido’, archivo: ‘factura-texto.pdf’ }, 

  { nombre: ‘PDF escaneado’, archivo: ‘albaran-escaneado.pdf’ }, 

  { nombre: ‘Imagen OCR’, archivo: ‘dni.jpg’ }, 

]; 

 

For (const c of casos) { 

  Test(`Extracción de ${c.nombre}`, async ({ page }) => { 

    Await page.goto(‘http://localhost:5173’); 

    Const fileInput = page.locator(‘input[type=”file”]’); 

    Await fileInput.setInputFiles(path.join(__dirname, ‘fixtures’, c.archivo)); 

    // Asumimos que la extracción se dispara automáticamente al cargar 

    // Esperar a que aparezca el resultado (ej. Un elemento con data-testid=”resultado”) 

    Const resultado = page.locator(‘[data-testid=”resultado”]’); 

    Await expect(resultado).toBeVisible(); 

    // Si expones un objeto global en desarrollo: 

    Const extraccion = await page.evaluate(() => (window as any).__resultado); 

    Expect(extraccion.texto).toBeTruthy(); 

    // Validar tipo documental, campos, decisión… 

    Await page.screenshot({ path: `evidencia/${c.nombre}.png`, fullPage: true }); 

  }); 

} 

``` 

 

Si necesitas más control sobre el proceso (ej. Esperar a que termine un worker), puedes escuchar eventos o exponer una promesa en window. 

 

 

¿Mantener extracción/OCR en frontend o mover a backend? 

 

Recomendación firme: mover la extracción y OCR a backend cuanto antes, aunque sea en un servicio mínimo. 

 

Por qué: 

 

· Testabilidad: un endpoint REST (Node + Express, Fastify, etc.) se prueba con herramientas convencionales (Jest + supertest) sin polifills ni navegadores. 

· Reutilización: email, WhatsApp, backoffice no tienen un navegador. Si la lógica solo vive en el frontend, tendrás que duplicarla o construir un adaptador extraño (ej. Un headless browser para cada canal). 

· Rendimiento/experiencia: tesseract.js en el navegador descarga modelos pesados (~10-30 MB), consume CPU y memoria, y es lento en dispositivos móviles. Un backend con Tesseract nativo o servicios cloud es mucho más rápido. 

· Escalabilidad: el backend puede escalar horizontalmente, usar colas (BullMQ, RabbitMQ) para OCR pesado, y gestionar límites de tasa. 

 

El coste de migrar ahora es bajo si lo encapsulas bien. Incluso en esta fase, puedes mantener una capa de abstracción: el frontend llama a un servicio interno IngestionService que, en desarrollo, podría seguir usando el navegador (con un adaptador temporal) pero en producción apunta a una API. Pero para multi-canal, el backend es imprescindible. 

 

 

Arquitectura mínimo sensato para futuro multi-canal 

 

Siguiente paso: un microservicio de ingesta documental (API REST) con procesamiento asíncrono opcional. 

 

Diseño simple: 

 

``` 

┌─────────┐    ┌──────────┐    ┌─────────────────┐ 

│  Web    │    │  Email   │    │  WhatsApp/BO    │ 

└────┬────┘    └────┬─────┘    └────────┬────────┘ 

     │  multipart   │  (webhook)        │  (webhook) 

     ▼              ▼                   ▼ 

  POST /api/v1/ingest   (multipart/form-data) 

     │ 

     ▼ 

 

│   Servicio Node.js (API)    │ 

│   - Acepta archivo          │ 

│   - Extrae texto: pdf-parse │ 

│     o pdfjs-dist en Node    │ 

│   - Si no hay texto → OCR   │ 

│     (tesseract.js en Node   │ 

│      o binario nativo)      │ 

│   - Clasifica y extrae      │ 

│   - Responde JSON con:      │ 

│      texto, tipo, campos,   │ 

│      decisión               │ 

 

``` 

 

Tecnologías sugeridas: 

 

· Framework: Express + multer para recibir archivos. 

· PDF con texto: pdf-parse (wrapper de pdf.js para Node, sin DOM) o pdfjs-dist en Node con el build legacy que no requiere canvas para extraer texto puro. 

· OCR: tesseract.js con node-canvas (funciona bien en Node) o mejor aún, un contenedor con Tesseract nativo + node-tesseract-ocr (más rápido). 

· Clasificación/extracción: lógica de reglas, expresiones regulares, o un modelo ligero (p.ej. transformers.js si es necesario). 

· Asincronía (si el OCR es lento): endpoint que devuelve inmediatamente un jobId y otro endpoint GET /status/:jobId para consultar. Así no bloqueas al cliente. Puedes usar BullMQ con Redis. 

 

Esta API puede desplegarse en un VPS, en un contenedor Docker, o en una función serverless (aunque el OCR pesado puede superar límites de tiempo). Para multi-canal, solo tienes que invocar el mismo endpoint desde el webhook del proveedor de email (ej. Mailgun, SendGrid) o de WhatsApp (Twilio). 

 

 

Alternativa ligera y robusta a tesseract.js en frontend o patrón híbrido 

 

Alternativa recomendada: patrón híbrido frontend/backend. 

 

· Frontend (ligero): solo extrae texto embebido con pdfjs-dist, que es rápido y consume pocos recursos. Si encuentra texto suficiente, clasifica directamente en cliente. 

· Backend (robusto): cuando el frontend detecta que no hay texto (PDF escaneado, imagen), envía el archivo al endpoint de ingesta para que haga OCR. 

 

Ventajas: 

 

· El caso más común (PDF con texto) se resuelve instantáneo, incluso offline o sin backend. 

· El OCR pesado se descarga en el servidor, donde puedes usar Tesseract nativo (binario, no JS) o servicios cloud sin penalizar al usuario. 

· No necesitas mantener tesseract.js en el frontend (ahorro de bundle y descarga de modelos). 

 

Alternativa robusta para OCR en backend: 

 

· Contenedor Docker con Tesseract 5 + lenguaje spa. La invocación vía node-tesseract-ocr o simplemente child_process.exec(‘tesseract input.png stdout’) es muy rápida y probada. Coste: cero. 

 

Si por restricciones de despliegue no puedes tener un servicio aparte, puedes usar tesseract.js en un Web Worker del frontend con un modelo más pequeño (solo español, sin LSTM) pero seguirá siendo pesado para imágenes de alta resolución. En ese caso, el híbrido te permite postergar la inversión sin renunciar a un camino serio. 

 

 

Camino más corto pero técnicamente serio para cerrar YA 

 

Si la prioridad es cerrar la validación de los tres casos sin rehacer toda la arquitectura, el plan mínimo viable es: 

 

1. Añadir un hook en tu app React: en modo desarrollo (import.meta.env.DEV), exponer el resultado final del pipeline en window.__resultado (un objeto con texto, tipo, campos, decisión). Esto es una línea al final del componente y no afecta a producción. 

2. Escribir un test con Playwright que cargue cada fichero de prueba, espere a que window.__resultado tenga un valor y lo valide con aserciones. Así tienes evidencia automatizada, repetible, que puedes ejecutar local y en CI. 

3. Generar evidencias: capturas de pantalla y un pequeño script que vuelque window.__resultado a un JSON para trazabilidad. 

4. Dejar documentado el plan de migración a backend como próximo paso (API de ingesta), pero sin implementarlo aún. Así cumples la validación inmediata y mantienes la dirección técnica correcta. 

 

Este enfoque: 

 

· No modifica la lógica de negocio. 

· No introduce polifills ni entornos falsos. 

· Es reproducible 100%. 

· Se puede entregar en horas/días. 

 

El test en Playwright se puede ejecutar contra el build de producción (vite build && vite preview) o contra el servidor de desarrollo, y queda listo para integrarse en el pipeline de CI cuando toque.

Así la validación es fuerte, pero no se rompe por una coma, un salto de línea o una ligera variación del OCR.

Alternativa ligera y robusta frente a tesseract.js 

Tesseract.js tiene sentido para pruebas, privacidad local y prototipos: es una versión JavaScript/WebAssembly de Tesseract, corre en navegador y Node, soporta muchos idiomas y usa workers. �
